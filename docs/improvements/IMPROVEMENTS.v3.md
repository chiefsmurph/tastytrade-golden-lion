## Code Quality

- [ ] **Close-side tick chase can leave two live sell orders** — `close-position.ts:135-150` treats cancellation as best-effort ("Best effort cancellation before placing next chase attempt") and the chase loop places the next order regardless. This is the exact race fixed in v1 for `manage-allocation.ts` (`placeRouteOrders` now breaks when a cancel can't be confirmed, `manage-allocation.ts:309-315`) — but the fix was never mirrored to the close path. A failed cancel + new sell order can double-sell the position (short exposure or rejection). Make `cancelOrderById` return success and break the chase loop on failure, same as the buy side.

- [ ] **Seed-time "no accumulation" gate is dead code** — `seed-symbol.ts:236-252` skips seeds when `candidate.strategy !== "MANAGE_ALLOCATION"`, but that field comes from `getDefaultTopCandidateSelection()` (`option-candidate/selection.ts:24-42`), which evaluates the strategy against dummy metrics (`bid=1, fill=1, lastActionTime=now`). With return 0% and 0 minutes since last action, `evaluateTradingStrategy` always lands in the cooldown branch and returns `MANAGE_ALLOCATION` — at any time of day. The skip reason "time-of-day strategy is not allowing new accumulation" can never trigger. Replace with an explicit minute-of-day cutoff check (the seeding-window helpers already exist).

- [ ] **Stop-loss is unreachable during the 10-minute cooldown** — In `evaluate-trading-strategy.ts`, the cooldown check (line 172) returns `MANAGE_ALLOCATION` *before* the intraday stop-loss floor is evaluated (line 181). `lastActionTime` refreshes whenever a fill updates the position (`evaluate-position.ts:124`), so the window where the stop is disabled reopens right after every avg-down buy — precisely when the position is falling. EOD liquidation is correctly checked before the cooldown; move the stop-loss floors above it too. Hard circuit breakers should never be subordinate to a cooldown.

- [ ] **Exposure-normalization logic exists twice** — `normalizeGroupExecutionTargetExposures` (`run-cycle-context.ts:217-259`) and `normalizeSelectedManageExposureTargets` (`execute-position-evaluations.ts:166-206`) are the same algorithm, maintained separately — the plan preview and the real execution can silently diverge. Same pattern as v2's `getMidpointPrice` item, which is *also* still duplicated (`manage-allocation.ts:79`, `close-position.ts:36`), as are `readEnvPct`/`toBooleanFlag` (`position-gate.ts:22-33`, `secret-auto-seed.ts:61-74`). Extract all three once.

- [ ] **Every cycle does the expensive work twice (or more)** — `buildRunCycleContext` runs a full dry-run plan (`manageAllocationForGroup` with `dryRun` → option-market snapshot, health gate across 3 DTE checkpoints each with serial per-candidate quote fetches, candidate selection, bid/ask), then `executePositionEvaluations` repeats all of it for real. On top of that, `getPositionEvaluations` for the *other* account is re-fetched up to 3× per cycle (cross-account gate lookup in `run-cycle-context.ts:350-388`, then again in each of the two seed paths in `run-cycle-seed.ts`), and each call re-streams live quotes for every position. Add per-cycle memoization (evaluations keyed by account; candidate/health results keyed by symbol+side+DTE) or thread the already-built context through.

- [ ] **`waitForOrderFill` polls the full order list every second** — Both copies (`manage-allocation.ts:215-246`, `close-position.ts:102-133`) call `getOrders(accountNumber)` once per second for up to 30s per tick, up to 10 ticks per route, per group — hundreds of full-list fetches per cycle. Use `getOrder(id)`, lengthen the poll interval, or watch order status via the account streamer. Also: an order that disappears from the list is treated as *filled* (`return true`), which silently mislabels cancelled/expired orders.

- [ ] **Execution results overstate fills and understate spend** — `placeRouteOrders` pushes `placedOrder: true` unconditionally after the chase loop (`manage-allocation.ts:354-358`), even if the last `createOrder` returned no order id, and `estimatedOrderValue` is computed from the *starting* limit price while the chase raises it toward the ask. `getUpdatedBudgetAfterAllocation` then decrements the budget with that stale estimate. Recompute value from the final chase price (or actual fills via the post-loop `getOrder` fetch the close path already does) so budget, run history, and `seedEstimatedTotal` reflect reality.

- [ ] **CLAUDE.md / README env names drifted after the prefix refactor** — Commit `5a72c04` renamed config to `STRATEGY_`/`CORE_` prefixes, but CLAUDE.md still documents `BOT_MIN_IV_RANK_PCT`, `BOT_MAX_OPTION_SPREAD_PCT`, `BOT_MARGIN_TARGET_CALL_DELTA`, `BOT_MARGIN_MAX_TARGET_DTE`, `BASE_URL`, `API_CLIENT_SECRET`, etc. Anyone setting the documented names gets silent fallback to defaults — this class of misconfiguration is invisible at runtime. Update the docs, and log the resolved config once at startup (with a warning for recognized-but-obsolete `BOT_*` names).
  **Partial progress 2026-07-02:** this bit for real — prod ran with a blank `TASTYTRADE_BOT_RUN_HISTORY_DIR=` that put `position-registry.json` in the project root, and `BOT_READ_ONLY_ACCOUNTS` was silently ignored by the old build. Fixed the adjacent drift: `BOT_RUN_HISTORY_DIR` removed entirely (path always derives from `BOT_DATA_DIR`), `ecosystem.config.cjs`'s dead `TASTYTRADE_BOT_SOCKET` removed, `ipc-client.js` aligned to the server's `CORE_IPC_SOCKET`. Still open: CLAUDE.md/README name updates and the startup config log.

- [ ] **`_PCT` env vars mix three different units** — Percent-scale (`STRATEGY_CROSS_ACCOUNT_YES_DOWN_PCT=10` → 10%, `STRATEGY_INTRADAY_STOP_LOSS_PCT=30` → /100 at read), fraction-scale (`STRATEGY_GATE_SINGLE_YES_MAX_TARGET_PCT=0.15`, `STRATEGY_MARGIN_MAX_BUY_EXPOSURE_PCT=0.12`), and pure multipliers (`STRATEGY_MARGIN_MAX_TARGET_MULTIPLIER=1.33`) are all read through the same style of helper in `position-gate.ts` / `risk-limits.ts`. Setting `STRATEGY_GATE_SINGLE_YES_MAX_TARGET_PCT=15` — the natural reading of "PCT" — yields 1500%. Standardize on percent everywhere with one shared reader that divides once, or rename fraction-based vars (`_FRACTION`).

- [ ] **Pacific-time schedules trust the server clock** — Every gate (`evaluate-trading-strategy.ts`, `position-gate.ts`, `seeding-windows.ts`, `close-position.ts` morning thresholds…) uses `Date.getHours()` and assumes the process runs in `America/Los_Angeles`. Nothing asserts it. On a mis-set box, the 12:55 PM margin liquidation, all cutoffs, and the exposure ramp shift silently by the TZ offset. Either assert `Intl.DateTimeFormat().resolvedOptions().timeZone` at startup and refuse to trade, or compute minute-of-day explicitly in the target zone.

- [ ] **The money-touching math has no tests** — Only 4 test files exist (`close-position`, `evaluate-trading-strategy`, `seed-symbol`, `seeding-windows`). Untested: `allocateContractsByWeight` (greedy remainder loop), `position-gate` scoring/tier selection, `seed-decision` threshold scaling — note `getScaledThresholds` (`seed-decision.ts:91-102`) can produce `minDownPct > maxDownPct` when the combined multiplier is high (e.g. 1.5×1.5 early morning on a new position), silently inverting the window into "never seed"; if that's intended, test it, if not, fix it — `signal-interpreter` weight math, and `overnight-reduction` target math (its age formula extrapolates for `ageDays < 1`). ~~Also: the two seed paths run under `Promise.all` (`run-cycle.ts:215-228`) and both do read-modify-write on `position-registry.json` — a lost-update race a test would catch.~~ *(Moot as of 2026-07-03: each account type takes exactly one seed path per cycle — the other returns immediately on the account-type check — so the concurrent read-modify-write can't occur for a single account's run. Test-file count is now 8, not 4; the specific money-math units listed here are still uncovered — see v4.)*

## Strategy

- [x] **The spread gate can veto the 12:55 EOD margin liquidation** — **[confirmed in run history]** `margin.ndjson` contains `"Morning spread gate active (55.53% spread > 30.00% max at 12:55)"` and again at 12:59. `getMorningCloseSpreadThresholdPct` (`close-position.ts:152-178`) plateaus at 30% after 8:00 AM and applies *all day, to every close* — including the hard EOD liquidation and stop-loss closes. A wide-spread loser is exactly the position you most need out of, and it's the one the gate protects. Exempt hard risk closes (EOD liquidation, stop-loss, overnight force-close) from the gate, or degrade to "peg mid and chase" instead of "don't close."
  **Fixed 2026-07-02 (partial by design):** all closes at/after 12:55 PM now bypass the gate (`EOD_FORCED_CLOSE_MINUTE` in `spread-thresholds.ts`), with tests. Morning stop-loss closes remain gated *deliberately*: the 2026-07-02 LCID incident showed bid-based stops in wide morning spreads are largely spread artifacts (-31% bid ≈ -20% mid), so the gate is protective there. The overnight force-close at open is also still gated — revisit if run history shows it being vetoed.

- [ ] **"target exposure is zero" is the #1 reason the bot doesn't buy** — **[confirmed in run history]** 146 of ~500 recorded skip reasons. The position gate multiplies group target exposure by `maxTargetPct` (`run-cycle-context.ts:432,479`), which is 0 when there's no cross-account confirmation and no secret stock signal (`position-gate.ts:219-231`). With the secret feed silent and no matching position in the sibling account, neither account can add to anything — contradicting "fully functional without the signal feed." Decide which it is: add a small unsignalled base tier (e.g. 0.05–0.10 of the time-of-day target) so the bot degrades to smaller-but-alive, or document no-signal = no-add as intended.

- [ ] **Health gate demands weekly liquidity for monthly buys** — **[confirmed in run history]** Dozens of skips like "option health gate failed for target DTE 25–30; missing healthy checkpoints: 7, 14". `evaluateOptionHealthForTargetDTE` (`option-candidate/health.ts:99-128`) requires *every* checkpoint ≤ targetDTE to be healthy, so a symbol with a liquid monthly but thin weeklies is unbuyable precisely in the morning when the DTE target is highest. Require only the checkpoint(s) bracketing the target DTE, and treat shorter-DTE health as a bonus signal, not a hard gate.

- [ ] **Margin buys 15–30 DTE options despite the 7-DTE cap** — **[confirmed in run history]** Margin plan rows show target DTEs of 15–30. Root cause is v2 item #4, still open: `getPositionGroupExecutionTargets` (`evaluate-trading-strategy.ts:365`) drops `accountType`, so per-group DTE comes from the *cash* branch (`max(raw, cashMinDTE)` → 30 in the morning) and averaging with the margin base (≤7) lands mid-teens to high-20s. A same-day gamma strategy paying 4-week theta is a different (worse) trade than designed. One-line fix; upgrade its priority.

- [ ] **Tick-chasing defeats the bid/mid/ask route design** — Every route chases toward the ask every 30s for up to 10 ticks (`placeRouteOrders`). With tick = max(spread/10, minTick), a "patient bid" order sits at ~mid after 5 minutes, and on tight spreads all three routes converge to the ask — the carefully time-blended route weights end up controlling only the *starting* price. Cap chase depth per route (bid: rest, don't chase; mid: 3 ticks; ask: full), and stop re-placing an identical price once the ceiling is hit (currently up to 10 pointless cancel/replace cycles at the ask). Bonus: worst-case chase time is 3 routes × 5 min per group, serial — one group can eat the whole 4-minute run interval, so late-day cycles run against a stale schedule.

- [ ] **No account-level daily loss circuit breaker** — Every risk control is per-position. After a bad open, nothing stops the machine from seeding and averaging down all day while account NLV bleeds: stop-losses realize each position's loss and the seed/gate logic happily re-enters. Add a kill switch — when NLV drops X% below the day's starting value (day-report-store already records baselines), block new allocations and seeds for the rest of the day, close-only mode. This supersedes v2's narrower "margin seeding ignores the margin account's own stress" (also still open — `pctOfNetLiq` is computed at `run-cycle-seed.ts:275-276` and then only logged, never gated on). Related and still open from v2: signal staleness — `secondsSinceLastPositionsUpdate` is already tracked in every run snapshot (`secret-socket-state.ts`), it just needs to be consulted before trusting `willBuy`/boolean scores.

- [ ] **Seed size is fixed at 1 contract regardless of conviction or premium** — `seedSymbol` always buys quantity 1 (`seed-symbol.ts:363-377`), so the dollar exposure of a "seed" is whatever the premium happens to be ($30 or $490 under the $500 cap) and conviction tiers (`goodBooleanScore`, loss depth, IV rank) change *whether* it fires but never *how much*. Size to a target dollar amount (`qty = floor(target$/premium)`) and scale the target with the boolean-score tiers that already exist in `getBooleanSurplusPct`. Also: cross-account seeds pay the full ask by default (`priceMode: "ask"`) — for an averaging-down thesis into weakness, start at mid with one re-price toward ask; the auto-seed path already uses mid.

- [ ] **Take-profit closes are all-or-nothing** — Hitting the dynamic profit target (40%→7%) liquidates the entire group in one shot. The partial-close plumbing already exists (`closePosition` `maxQuantityToClose`, used by overnight reduction). Scale out instead: close ~half at target, hold the rest with a stop raised to the target price — on trend days the strategy currently sells its best positions at the first target while riding losers to the stop. (v1's time-based-stop idea for the loss side is still open and pairs well with this.)

- [ ] **Same-symbol re-entry after a profitable close is still unguarded — and the building block already exists** — v2 item #1, still open. `position-registry.ts` now exports `isClosedToday`/`isOpenedToday`, but nothing consumes them: run-cycle seeding only excludes symbols closed *in the current run* (`closedUnderlyingSymbolsThisRun`), and secret auto-seed only has its 10-minute cooldown map. Wire `isClosedToday` (or a time-boxed variant, e.g. closed within 60 min) into `seedSymbol` and the gate so the bot stops buying back premium it just sold at a worse basis.

- [ ] **The IV gates may be silently inert — verify the scale and availability** — Zero "IV rank … below minimum" skips appear anywhere in run history, and no `ivRank` values are recorded. Two possible causes, both bad: (a) `getUnderlyingIvMetrics` returns `null` in practice (API shape mismatch in `market-metrics.ts:34-48`), in which case the entry IV gate (`selection.ts:285-293`) and the seed IV fallback (`seed-decision.ts:141-156`, thresholds 50/70) silently pass/fail without ever engaging; or (b) the Tastytrade API returns `implied-volatility-index-rank` on a 0–1 scale (as its public docs suggest) while the code compares against 20/50/70 on a 0–100 scale. Log the raw metric once per cycle, normalize (`value <= 1 → ×100`), and add a unit test pinning the expected scale. Until verified, IV-rank-based entry quality — a v1 headline feature — may not be doing anything.

## Addendum — fixed 2026-07-02 (not previously tracked)

Driven by a live incident: LCID stop-out at "-31.15%" bid into a 28.57% spread at 07:46, close vetoed by the spread gate, then closed at 0.43 and re-bought at 0.45 minutes later. Root cause analysis exposed a structural coupling: entries were allowed at spreads up to 30% (`STRATEGY_MAX_OPTION_SPREAD_PCT`) while the stop loss fires at -30% measured at *bid*, so a max-spread ask fill is born ~4 points from its own stop.

- [x] **Buy-side morning spread ramp** — entries now use `getMaxOptionSpreadPctForTime` (min of configured cap and the same 5%→30% morning schedule the close gate uses, extracted to `strategy/spread-thresholds.ts`). Positions can no longer be born pre-triggered before 8:00 AM.
- [x] **Position registry never learned about regular buys** — `recordPositionOpened` was only called from the two seed paths, so `isOvernightPosition` returned false for normally-bought positions and the overnight reduction/force-close logic silently skipped them. Now `syncPositionOpens` backfills opens from broker `created-at` every cycle (self-healing, covers pre-existing and manual positions), and `recordPositionClosed` takes a broker-timestamp fallback instead of fabricating `openedAt` = close time.
- [x] **"No candidate found" starved groups the bot already holds** — `manageAllocationForGroup` re-selects from the chain every cycle and never considered the held contract; the cash afternoon DTE window (0–14) excluded a held 15-DTE seeded contract, so the group could never be added to. Now falls back (fallback only, chain pick stays authoritative) to the dominant held contract, gated by the time-aware entry spread limit, a DTE floor (cash ≥1, margin ≥0), and never past the IV-rank gate (`skippedByIvGate`).
- [x] **Stale test** — "keeps cash accounts active at 12:30" expected exposure 0.8 from a pre-`fe30c51` schedule; the 12:45 cash exposure peak makes 0.98 correct.

Deferred by choice (design ready, wants post-fix run-history evidence first): stop-loss grace period for positions <90–120 min old with a mid-based catastrophic floor, and a time-based re-entry cooldown after stop-outs. Test files went from 4 to 7; the money-math units listed in the tests item above remain uncovered.
