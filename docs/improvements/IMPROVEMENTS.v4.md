## New findings (v4)

### Bugs / correctness

- [ ] **Dry-run plan sizes margin buys with the cash per-action cap** — `manageAllocationForGroup` reads `getMaxBuyExposurePctForAccountType(options.accountMarginOrCash ?? "cash")` (`manage-allocation.ts:497`), and the planning loop in `run-cycle-context.ts:591-597` passes only `{ dryRun: true }`. Real execution passes the account type (`execute-position-evaluations.ts:317`), so live orders are right — but the plan preview, plan diagnostics, planned rows, and the planning budget recorded to run history understate margin per-action capacity ~2.4× (5% vs 12%). Every "insufficient budget for one contract" in a margin plan is suspect until this is fixed. One-line fix: pass `context.accountMarginOrCash` into the dry-run call.

- [ ] **The gate's exposure *scaling* is cancelled by normalization — only the ceiling survives** — `run-cycle-context.ts` scales each group's `targetAccountExposure` by `gate.maxTargetPct` with the stated intent "ramps toward the gate ceiling by end of day rather than hitting it immediately" (comment at `run-cycle-context.ts:476-478`). But `normalizeGroupExecutionTargetExposures` / `normalizeSelectedManageExposureTargets` then rescale the selected groups so they *sum to the account schedule* — a lone gated group at 0.05 gets normalized right back up to the full account target, and only the `min(target, maxTargetAccountExposure)` clamp in `manage-allocation.ts:490-494` does real work. Net effect: a gated position jumps to its gate ceiling immediately (throttled only by per-action caps), and relative conviction weighting between groups is mostly lost. Either normalize *after* clamping (cap-aware normalization that redistributes surplus to unclamped groups), or accept ceiling-jump behavior and delete the misleading scaling+comment.

- [ ] **Close-side tick chase can still double-sell** — carried from v3, re-verified: `cancelOrderById` in `close-position.ts:139-154` swallows cancel failures ("Best effort cancellation") and the loop places the next sell regardless (`close-position.ts:306-314`). The buy side breaks the chase when a cancel can't be confirmed (`manage-allocation.ts:331-337`); mirror that. This is the one remaining unguarded double-order race in the money path.

- [ ] **`waitForOrderFill`: missing order = "filled", and it polls the full order list every second** — both copies (`manage-allocation.ts:237-268`, `close-position.ts:106-137`). An order that drops out of the list (cancelled/expired/rejected) is reported as filled, which feeds the chase loop and the results. Use `getOrder(id)` and treat not-found as not-filled; lengthen the poll interval.

- [ ] **Buy results still overstate fills and understate spend** — `placeRouteOrders` pushes `placedOrder: true` unconditionally after the chase (`manage-allocation.ts:376-380`), and `estimatedOrderValue` stays at the *starting* route price while the chase walks toward the ask. The close path already re-fetches the final order to capture fills (`close-position.ts:345-360`) — do the same here so the budget decrement, run history, and `allocationEstimatedTotal` reflect what was actually spent.

- [ ] **Stop-loss is still subordinate to the 10-minute cooldown** — `evaluate-trading-strategy.ts:177` returns `MANAGE_ALLOCATION` before the intraday floor at `:186`, and `lastActionTime` refreshes on every fill (`evaluate-position.ts:124`), so the stop is disabled for 10 minutes after each avg-down buy — exactly when a falling position needs it. Move the risk floors above the cooldown (EOD liquidation already is). Pairs with the deferred grace-period design below; do them together so young positions get a grace window measured at mid, not a hole after every fill.

- [ ] **Secret signals are consumed with no staleness bound** — the disk cache rehydrates only if <10 min old, but the in-memory cache is trusted forever: `getCachedSecretSourcePositions()` feeds `countGoodBooleans`, gate tiers, `willBuy` (worth 2 points), buy weights, and seed decisions with no age check. `secondsSinceLastPositionsUpdate` is tracked, logged, and recorded to run history — but nothing gates on it (the only consumer is a log string in `seed-decision.ts:161`). The secret program liquidates EOD, so a 2-hour-old bullish snapshot is actively wrong in the afternoon. Add a max-age (suggest 15–20 min) beyond which the boolean score degrades to `null` (which already routes to the IV fallback / no-seed path), and stamp `signalAgeSeconds` into the gate log lines.

- [ ] **`getScaledThresholds` can silently invert the seed window** — with the new fill factor the combined multiplier reaches 1.5⁴·(≤1.0) ≈ 3.4 (early + brand-new + margin barely deployed): min 8% → 27% scaled while max stays capped at 20% → `minDownPct > maxDownPct`, window empty, seed silently impossible (`seed-decision.ts:104-116`). If "all-conservative = don't seed" is intended, log it explicitly and add a test asserting the inversion; if not, clamp `minDownPct = min(scaled, maxDownPct - ε)`. `risk-limits.test.ts` covers the individual multipliers but not the stacked inversion.

- [x] **Liquidity checks were mostly decorative — data foundation fixed 2026-07-03, policy tracked as strategy #4** — verified live with `src/tools/probe-option-chain.ts`: the streamer sampling pipeline works (ATM strikes carry volume/IV/delta; margin delta-targeting correctly picks the ~0.39-delta strike first), but the consumers were weaker than they looked. (a) `meetsVolumeRequirement` (>40) is computed and never filtered on — flag + last-place sort tiebreak only; the spread gate is the sole liquidity rejection. Still true; addressed by strategy #4 step 3. (b) ~~openInterest existed only as a fallback value `max()`-merged into volume~~ **fixed**: OI is now extracted and merged separately (`callOpenInterest`/`putOpenInterest`, `OPEN_INTEREST_FIELD_NAMES` in `option-service.ts`, unit-tested) — live probe shows genuinely different numbers (MARA 14-DTE: volume 2,404 vs OI 10,443). (c) ~~bid/ask sizes never captured~~ **fixed**: `getBidAskForSymbol` returns `bidSize`/`askSize` and candidate results carry them. Gating policy for all three lives in strategy #4.

- [ ] **Dead/cosmetic**: `closeEvaluations` is computed and never used (`execute-position-evaluations.ts:210-212`); secret auto-seed logs "booleans N/**5** good" for a 0–10 score (`secret-auto-seed.ts:176`); `getCrossAccountYesDownPct`'s comment says the window starts 9:30 but the default `SECRET_AUTO_SEED_START_TIME` start is 6:30 (`position-gate.ts:37-51`); when `average-open-price` is missing, `weightedAverageFill` falls back to the current bid (`evaluate-position.ts:113-116`), silently pinning the group's return at 0% and disabling its circuit breakers — worth a warn.

## Strategy / profitability — ranked by expected dollar impact

1. [ ] **VERIFY, then decide: does "target exposure is zero" collapse now that the crash loop is fixed?** — **[prod]** 84/108 cash entries and 42/121 margin entries on 07-02 hit this skip. The dominant cause on that day was *not* structural: the dxLink UNAUTHORIZED crash loop restarted the process 38×, and every restart blanked the in-memory secret cache, so cycles right after a boot saw 0 positions → booleans 0 → `computePositionGate` = 0. Both halves of that were fixed the evening of 07-02: persisted restart backoff + narrowed fatal matcher (restarts should be rare), and positions **and** tickerRecs persisted to `data/secret-cache.json` and rehydrated on boot if <10 min old. So the first move is measurement, not code: on the next trading day, recompute the zero-target rate (`plan.diagnostics` skip counts per account) and expect it to drop to a small residual. What will *still* legitimately zero out even with a healthy feed: (a) symbols the secret program doesn't track (booleans stay 0; no basic tier possible; crossAccountYes only if the sibling holds the name and it's down past threshold), (b) restarts where the cache file is >10 min stale (cold until the next push), (c) genuine extended feed outages. Only if the residual is still material, revisit the v3 remedy: a small unsignalled base tier (e.g. 0.05–0.08 of the time-of-day target, optionally IV-gated once the IV metric is fixed) vs. documenting no-signal = no-trade and surfacing it loudly in the run summary.

2. [ ] **Margin still buys 15–30 DTE despite the 7-DTE cap** — carried from v2/v3, re-verified in current code: `getPositionGroupExecutionTargets` calls `getTimeOfDayExecutionTargets(currentTime)` without the account type (`evaluate-trading-strategy.ts:370`), so the per-group DTE takes the cash branch (morning 30) and the blend in `buildGroupExecutionTargets` lands mid-teens+. A same-day gamma strategy paying 3–4 weeks of theta on every add is a persistent, quantifiable drag. Thread `accountType` through `GroupExecutionTargetInputs` → `getPositionGroupExecutionTargets`; ~5 lines plus a test.

3. [x] **IV gates: root cause confirmed live and FIXED 2026-07-03 (pending deploy)** — **[prod]** `"ivRank":null` in 14/14 occurrences on 07-02; zero IV-gate skip messages in all recorded history. Root cause, confirmed with `src/tools/probe-iv-rank.ts` (added this pass) against the live API: the SDK serializes query params with `qs.stringify(..., { arrayFormat: 'brackets' })`, so `getMarketMetrics({ symbols: [key] })` went out as `symbols[]=MARA`, which the API rejects with a bare **400** → caught → cached `null`, silently, since the feature shipped in v1. The comma-string form returns real data, and the scale is confirmed **0–1** (MARA `"0.355173693"`). Fix shipped as one unit per the ordering warning: `symbols: key` string form + `parseUnderlyingIvMetricsEntry` normalizing ≤1 values ×100 + `market-metrics.test.ts` pinned to the live captured payload. Post-fix probe through the bot's own code: MARA 35.5, SPY 33.0, **LCID 15.1 — below the entry minimum of 20**, meaning the gate would have blocked the 07-02 LCID churn symbol on 07-03. Remaining follow-ups: verify in prod logs after deploy (Monday check #6), and revisit the seed IV-fallback bars (50 early / 70 deep) against real rank distributions — MARA at 35 would not qualify, so the no-boolean fallback may still rarely fire in practice.

4. [ ] **Incorporate liquidity data properly: day volume, open interest, quote sizes** — flagged top-priority by the user 2026-07-03; the foundation SHIPPED the same day (verified live: OI now tracked separately from volume as `callOpenInterest`/`putOpenInterest` — MARA 14-DTE showed volume 2,404 vs OI 10,443, numbers the old `max()` merge would have conflated — and `getBidAskForSymbol` now returns `bidSize`/`askSize`; all of it rides into candidate results and the `Top option candidate` logs). Roles, kept distinct: **delta** stays the exposure/movement selector; **day volume** answers "can we exit at fair prices *today*" (weight heaviest for margin, which must exit by 12:55); **OI** answers "does a standing market exist" (weight heavier for cash overnight holds; stable intraday so it's safe to floor-gate); **sizes** answer "is the quoted spread real" (execution tactics + phantom-quote defense). Rollout in three deliberate steps — NOT all at once, so Monday stays interpretable for the IV-gate go-live: **(1) log-only** — collect a few sessions of volume/OI/size distributions from the candidate logs; **(2) floor gates on new entries** — `STRATEGY_MIN_OPEN_INTEREST` (e.g. 100) plus a phantom-quote guard (sizeless quote while the market is open ⇒ don't trust this cycle's spread-gate pass); **(3) scoring + tactics** — replace the decorative `meetsVolumeRequirement` flag and last-place volume tiebreak with a liquidity score among spread-passing candidates (log-scaled volume + OI; volume-weighted for margin, OI-weighted for cash), and teach the tick-chaser to respect sizes (don't chase an ask showing less size than the order; prefer patient mid on thin bids for closes). Enabler for step 3: extend the `fetchOptionVolumes` streamer listener to also capture Quote events (bid/ask/bidSize/askSize per strike) — they already arrive on the existing 5–7s subscription and are ignored, so this yields spread% + sizes for the *whole* considered set at zero extra session/time cost, and lets selection pre-filter by spread before any serial quote fetches (faster cycles). Post-Monday only — it touches the production sampling path. Constraint for every gate: sampling only covers ~ATM strikes inside the target DTE window, so *unknown must degrade gracefully* (pass + log) — never treat missing data as zero.

5. [ ] **Stop-loss grace period + mid-based catastrophic floor (deferred in v3, now unblocked)** — **[prod]** the 07-02 LCID churn (born at -26% bid in a wide spread, stopped at "-31%" that was ~-20% mid, re-bought minutes later) is the template. `openedAt` is now reliable via `syncPositionOpens`, which was the stated blocker. Design from the fix menu: positions <90–120 min old skip the bid-based stop but keep an always-live floor at **mid** (~-50%); pairs with the cooldown-ordering fix above. Also new supporting evidence for wide-spread handling: a cash close was vetoed at 12:49 by a 66.67% spread (**[prod]**) — for gated stop closes, degrade to "peg mid, chase patiently" instead of "don't close," so a real collapse can't strand a position for hours behind its own spread.

6. [ ] **Re-entry after a close is still completely unguarded** — `isClosedToday`/`isOpenedToday` exist (`position-registry.ts:177-194`) and still have zero consumers; `recentlyClosedByAccount` only covers the current pass, and the auto-seed cooldown map resets on restart. The bot can stop out and re-buy the same premium minutes later (LCID did exactly this, twice). Wire a time-boxed check (closed within N minutes, default ~60) into `seedSymbol` and the gate path. Deliberately time-boxed, not "only below exit price" — the 07-02 re-buy at 0.45 that reset a wedged anchor was beneficial.

7. [ ] **Seed size is still fixed at 1 contract, and seeds ignore the boolean surplus** — quantity is hardcoded (`seed-symbol.ts:390-396`) so conviction changes *whether*, never *how much*; and the per-action cap for seeds (`effective-buying-power.ts:53-56`) does not add `booleanSurplusPct` the way allocation buys do (`manage-allocation.ts:498-499`), so a 9/10-conviction cash seed is still capped at 5% × ~$2k ≈ $100 — below most ITM candidates (seed-blocker #1 from 07-02 is only *softened* by the held-contract cost fallback, not fixed). Size to a conviction-scaled dollar target (`qty = floor(target$/premium)`), apply the surplus to the seed cap, and let `BOT_MAX_SEED_ORDER_COST` + the `maxLimitPrice` entry-quality gate remain the hard ceilings.

8. [ ] **Take-profit is still all-or-nothing** — the partial-close plumbing (`maxQuantityToClose`) is battle-tested by overnight reduction now; scale out (~half at target, trail the rest with the stop raised to entry-of-the-runner) instead of selling the whole best position at the first target while losers ride to the stop.

9. [x] **Tick-chasing defeated the route design — semantics redesigned with the user 2026-07-03, implemented same day, shipping in Monday's deploy** (originally fenced to Tuesday; folded into Monday on the user's call — bid-chases-ask is a mislabeled bug not a design under test, one day of data isn't a signal worth protecting, and per-order logging keeps the three Monday changes disentangled) — the old behavior: all three routes chased to the ask (`placeRouteOrders`), so bid/mid/ask weights only picked the starting price — a "patient bid" order sat at ~mid in 2.5 minutes, a mid order paid the full ask in 5, and the ask route paid the full spread *instantly* then burned up to 10 cancel/replace cycles at the identical price. New semantics — the route name describes how much spread the order concedes and how fast, not a starting price: **bid** rests at the bid and never chases (a genuinely patient order); **mid** starts at mid and concedes at most 3 ticks; **ask** starts at **mid** and chases to the full ask on a faster clock (15s ticks → reaches the ask in ~2.5 min instead of paying it immediately — user's "ask = mid + chase" design), except when the spread is within two min-ticks (nothing to capture → straight to the ask). Identical-price re-placement is stopped, and a chase step only follows a *confirmed* cancel (the buy side now shares the close side's no-double-order guard). Request count is flat-to-lower: the wasted same-price replacements are gone and fill-polling is single-order. Residual risk, accepted: the ask route's fill can lag by up to ~2.5 min in a fast market — bounded by the faster clock. Still open from the original item: worst-case serial chase time per group vs the run interval (unchanged), tracked with the per-cycle memoization item.

10. [ ] **Still no account-level daily-loss circuit breaker** — every control is per-position while the seed/gate machinery can average down all day. Day-report baselines exist (`day-report-store.ts`); when NLV drops X% below the day's start, flip to close-only for the day. The new `fillRatio` axis actually *increases* cash's willingness to press as margin gets fuller — a good idea that specifically needs this backstop.

11. [ ] **Asymmetry: the margin-from-cash seed path has no held-contract fallback** — `maybeSeedCashAccountFromMarginAccount` retries the exact held contract on DTE/cost skips; `maybeSeedMarginAccountFromCashAccount` (`run-cycle-seed.ts:108-246`) gives up on the first skip. Margin's OTM delta-targeted picks are usually cheaper so this bites less often, but on a cost-blocked morning the cash side holds the exact (often cheaper) contract margin wants. Mirror the fallback with the margin DTE floor (≥0).
