## Code quality / correctness

1. [ ] **`getBidAskForSymbol` accepts one-sided quotes — fake 0% spreads and phantom mids** — `withQuoteSubscription` resolves on the *first* event carrying a bid **or** an ask (`market-data.ts:155-160`). A bid-only event flows into callers as `ask = bidAsk?.ask ?? bid` (`manage-allocation.ts:661-662`), so spread = 0 → the entry spread gate passes vacuously, the "midpoint" is the stale bid, and `getRouteChasePlan` sees a tight spread and sends the ask route straight to what it thinks is the ask. The inverse (ask-only) makes `getSpreadStats` compute a 200% spread and reject a possibly fine candidate. Fix in the fetch layer: accumulate fields across events and resolve early only when both sides are present; return whatever accumulated at timeout. *Adjacent to v4 strategy #4 step 2's phantom-quote guard, but different failure mode — that one is about sizeless two-sided quotes; this is the fetch accepting half a quote.*

2. [ ] **Hot-path debug log prints every quote event, including non-matching ones** — `market-data.ts:114`: `console.log("Received quote event:", event)` runs inside the listener for every event during every `getBidAskForSymbol` / `getUnderlyingPrice` subscription window, *before* the symbol-match check. There are dozens of these subscriptions per cycle (every position snapshot, every candidate probe, every health checkpoint), each printing every event that arrives in its window. Almost certainly the single noisiest line in prod logs, and pure CPU/disk waste. One-line deletion; does not need to wait for the pino migration (v4 "Older ideas" / STATUS structured-logging item).

3. [ ] **Registry and run bookkeeping record on order *placement*, not fill** — `recordPositionClosed` fires whenever a close order was placed (`execute-position-evaluations.ts:261-277`), but `closePosition` pushes `placedOrder: true` unconditionally after its chase loop (`close-position.ts:332-339`) and the order can rest unfilled at mid until the next cycle's sweep cancels it. Same on the open side: both seed paths call `recordPositionOpened` immediately after placing a resting limit (`run-cycle-seed.ts:206-208`, `:398-400`; `seed-symbol.ts:492-514` never waits for a fill). Consequences: phantom `closedAt` entries in the registry, `closedUnderlyingSymbolsThisRun` blocking overnight reduction and seeds for positions that never actually closed, `get-closed-positions-today` counting placements, and — once v4 strategy #6's re-entry cooldown ships — cooldowns keyed off closes that never happened. Fix: confirm via `getOrder` before recording (the close path already re-fetches the final order for fills — use its status), or reconcile the registry against broker positions next cycle. *Sibling of v4 bug #37 (buy results overstate fills), which covers the results/budget side but not the registry writes.*

4. [ ] **`placeRouteOrders` is untestable — and it's the code shipping Monday** — `closePosition` takes injectable `createOrder`/`cancelOrder`/`checkOrderFilled` dependencies (`close-position.ts:25-38`) and has a 295-line test exercising its chase loop. `placeRouteOrders` hard-imports the API client (`manage-allocation.ts:310`), so the redesigned route-chase semantics (v4 strategy #9: confirmed-cancel-or-break, ceiling stop, fast ask clock) are tested only via the pure `getRouteChasePlan` helper — the loop that actually spends money has zero coverage. Mirror the close path's dependency pattern and port its test structure. Test-only refactor, no behavior change — eligible to land before Monday, and most valuable *before* Monday.

5. [ ] **Symbol keying drops `::side` at five call sites — put/call groups on the same underlying collide** — the codebase's own group key is `UNDERLYING::side`, but: the cross-account confirmation map is keyed by underlying only (`run-cycle-context.ts:351-389`), so a cash RUM *put* return "confirms" a margin RUM *call*; `gateBySymbol` in `computeGroupReturns` (`run-cycle-context.ts:140-145`) and the DO_NOT_TOUCH decision annotation (`run-cycle-context.ts:300-318`) match by underlying, so one side's gate/annotation overwrites the other's; `withOvernightCloseOverrides` checks `isOvernightPosition(account, symbol)` (`run-cycle.ts:61`), so an overnight call force-closes a same-day put on the same name; and registry keys are `account:SYMBOL:date` with side stored but not keyed (`position-registry.ts:27-29`), so `recordPositionOpened` for the second side early-returns at `:77` and that side never registers. Low frequency today (the strategy is call-dominant) but every one of these is a silent wrong-answer when a put shows up. Unify on `groupKey`.

6. [ ] **Two `getPositionAgeDays` with the same name and different units** — the registry export returns rounded *calendar-day* deltas (`position-registry.ts:152-165`); the local one in the seed path returns *fractional elapsed* days with a broker `created-at` fallback (`run-cycle-seed.ts:61-78`). They feed different age multipliers (`getPositionAgeSeedMultiplier` expects days, `getPositionAgeMinutesSeedMultiplier` gets the fractional one converted to minutes) and anyone touching one will reasonably assume the other's semantics. Consolidate into the registry behind one API with an explicit fractional option. *The seed-decision test item in v4 #94 covers the multipliers' math, not this ambiguity.*

7. [ ] **`cancelAllLiveOrders` runs twice per cycle** — once at `run-cycle.ts:189` (useful: frees BP reserved by working orders before balances are read) and again inside `executePositionEvaluations` (`execute-position-evaluations.ts:143`) after the slow planning phase. Between the two sweeps nothing places unprotected orders — auto-seed orders carry protected sources the sweep skips anyway — so the second sweep is a redundant full order-list fetch + N cancels per cycle. Keep one, placed deliberately (the second call site matters only for direct/IPC invocations of `executePositionEvaluations`, which can keep it behind a flag). Interacts with strategy #1 below — if working orders become persistent, this consolidates into the diff logic.

8. [ ] **The weighted close price is dead code** — `buildClosingOrderPayload` computes a bid/mid/ask-weighted price from the route weights (`order-utils.ts:92-96`), but `closePosition` sets `currentPrice = midpointPrice` (`close-position.ts:263`) and overwrites `price` on every order it builds (`close-position.ts:279-282`). Route weights have never affected closes; the weighted computation only serves as a `> 0` sanity check. Delete it (and pass only what's needed into `buildClosingOrderPayload`) or actually wire it up — as-is it misleads anyone reasoning about close pricing, and it cost this pass an hour of "wait, do closes respect weights?".

9. [ ] **A failed cycle leaves no trace in run history** — any throw inside `runBotCycle` (network blip in `executePositionEvaluations`, API 500 mid-loop) aborts before `appendRunHistory` (`run-cycle.ts:289`); the scheduler catches it and stores the message in in-memory state only (`market-open-scheduler.ts:109-113`), gone on restart. Post-day NDJSON analysis cannot distinguish "no cycle ran in this window" from "cycle exploded halfway through execution" — which matters exactly when orders may have been placed before the throw. Append an error-typed run-history entry carrying the error plus whatever partial results exist. Additive diagnostics, no trading behavior change.

10. [ ] **Every chain snapshot pays two serial streamer sessions plus three full-chain deep clones** — `fetchOptionChainWithVolume` samples the ATM band for 5s, then the mandatory ITM strikes for 7s, back to back (`option-service.ts:509-510`), behind the global streamer mutex — ≥12s of serialized wall clock per symbol per cache miss, before the per-candidate quote fetches start. Subscribing the *union* of both symbol sets in a single ~7s session preserves both samples' coverage and halves the streamer time per symbol. While in there: `mergeVolumesIntoChain` ×2 + `mergeGreeksIntoChain` each `JSON.parse(JSON.stringify(...))` the whole chain (`option-service.ts:440,482`) — merge in one pass. *Complements v4's per-cycle memoization item (#88): that item reduces how often this call runs; this reduces what one call costs.*

## Strategy / profitability

1. [ ] **Let resting orders survive across cycles (diff-based order management)** — the redesigned bid route "rests at the bid and never chases" (v4 strategy #9), but every cycle opens with a cancel-all sweep (`run-cycle.ts:189`; the route code itself says "the next cycle's cancelAllLiveOrders sweep owns cleanup", `manage-allocation.ts:363-367`). So a "genuinely patient" bid order lives at most one run interval (~4 min) and surrenders its place in the order-book queue on every cancel/re-place — queue priority is where passive fills actually come from, and the bot re-buys the back of the line every cycle. Fix: diff the new cycle's desired orders against live orders and leave matching ones (same contract, price, quantity) working; cancel only what changed. The protected-source mechanism in `cancelAllLiveOrders` (`execute-position-evaluations.ts:95-111`) already proves selective sweeps work. Subsumes code #7 when done.

2. [ ] **Nothing models fees — sub-$1 contracts churn away the profit target** — there is no commission/regulatory-fee accounting anywhere in sizing, targets, or P&L. `allocateContractsByWeight` (`manage-allocation.ts:119-187`) happily buys many cheap contracts; on a $0.43 LCID contract a ~$1.30 round trip is ~3%, against a late-day take-profit of 7% (`getDynamicTakeProfitTarget`) — nearly half the target is friction, invisible to every decision. Add a per-contract friction constant (env: commission + fees per side) to the take-profit/stop math, and a minimum-premium floor for entries so the bot prefers fewer, richer contracts over confetti. The 07-02 LCID churn (v4 strategy #5/#6) was also a *fee* incident — every re-entry paid the toll twice.

3. [ ] **Exposure is measured at market value, so losses refill their own headroom** — `portfolioExposure` starts as bid-marked group value (`buildInitialBudget` → `getGroupMarketValue`, `manage-allocation.ts:863-876`, `order-utils.ts:126-131`) and `exposureHeadroom = targetExposure − portfolioExposure` drives every buy. When positions decay, exposure falls and headroom reopens — the bot automatically replaces burnt premium all day, a structural drip-martingale that operates *below* the threshold where the planned daily-loss breaker (v4 strategy #10) would trip. Note the accounting is also internally inconsistent: within a cycle the budget increments at *cost* (`getUpdatedBudgetAfterAllocation` adds `estimatedOrderValue`) onto a baseline marked at *market*. Track exposure at cost basis (or cap gross daily buys per account). Distinct lever from the daily-loss breaker: that stops the machine after a drawdown; this removes the mechanism that feeds it.

4. [ ] **Capital priority is losers-first** — the plan sorts selected groups by `currentReturn` ascending (`run-cycle-context.ts:524`) and `sortManageEvaluationsByTargetExposure`'s tiebreak does the same (`group-allocation-priority.ts:16-18`), so the deepest drawdown eats the per-group budget split first and winners get remainders. The seed paths gate averaging-down on conviction (booleans, IV, entry quality) — the main allocation loop is the one place that still rewards pain directly. Rank by conviction instead (gate `maxTargetPct`, boolean score, buyWeight), losers last. *Different axis from v2/v4's "bid-lean adds on profitable positions" (route weights); this is who gets the money at all.*

5. [ ] **Circuit breakers blend all expirations in a group** — groups key by `UNDERLYING::side` and `buildAggregateMetrics` produces one quantity-weighted return across every contract held (`evaluate-position.ts:53-73`, `:138-185`). A healthy 30-DTE leg can mask a collapsing 3-DTE leg so the stop never fires on it, and one take-profit liquidates every expiration at once. Evaluate the stop/target per expiration (the partial-close plumbing already takes `maxQuantityToClose`, `close-position.ts:37`) while keeping allocation at group level. *Pairs with v4 strategy #8 (scale-out) — that item splits the close by quantity; this splits the trigger by expiration.*

6. [ ] **Nothing looks at the underlying before averaging down** — adds and seeds fire purely off option-mark loss depth plus secret/cross-account signals; no code consults the underlying's intraday tape, so averaging-down buys land into free-fall. A cheap stabilization gate before any averaging-down buy — underlying above its N-minute low, or two consecutive cycles of non-decreasing marks (the run-history entries already carry per-group marks each cycle) — would have blocked the worst 07-02-style entries. Distinct from the signal gates: those are the secret program's opinion; this is the actual price. Cheap to log-only first (v4 #4-style rollout): record "would have blocked" for a week before enforcing.

7. [ ] **The IVX tiebreak prefers the richest vol — a premium buyer overpaying on purpose** — candidate sort at `selection.ts:176-181`: when two candidates' DTE deltas are within 3, the *higher* IV expiration wins. Buying the higher-IVX expiration means paying more for the same exposure. The v1 rationale (richer premium ≈ more activity) is better served by the actual liquidity data now captured (volume/OI/sizes, v4 strategy #4). Invert to prefer cheaper IVX, or fold into the v4 #4 step-3 liquidity score and delete the tiebreak.

8. [ ] **Close urgency is one-speed — the 12:55 liquidation can still be chasing at the 1:00 bell** — every close chases mid→edge on a 30s clock with up to 10 moves (`close-position.ts:11-13`): worst case ~5 minutes. The margin EOD trigger fires at 12:55 (`evaluate-trading-strategy.ts:158`), and with a 4-minute run interval the cycle evaluating it may start at 12:58 — the chase can still be walking toward the bid when equity options close at 1:00 PT, which is exactly the overnight-margin-exposure outcome the liquidation exists to prevent. Tier the chase by urgency: hard-risk closes (EOD, stop-loss) tick every 5–10s and cross to the bid on the final moves; consider arming the EOD path at ~12:50 so a full chase fits. *v3/v4 fixed the spread gate vetoing EOD closes; nobody has audited the clock.*

9. [ ] **Persist a realized-P&L attribution ledger** — `get-closed-positions-today.ts` already reconstructs per-close realized P&L from run-history fills, but only for today, on demand, close-side only; the day report records unrealized marks only. Persist every round trip as it completes, tagged with decision type (stop / take-profit / EOD / overnight-reduction / seed source / manual), route, entry spread, hour, DTE at entry, and gate score at entry. Nearly every AFTER-MONDAY tuning item in STATUS says "tune from distributions" — this produces those distributions continuously instead of via manual data-pull sessions, and if it lands before Monday, Monday's session is captured in it. Zero trading behavior change.

10. [ ] **Margin's delta target is flat 0.35 all session while its DTE ramps to ≤7** — `STRATEGY_MARGIN_TARGET_CALL_DELTA` (`entry-filters.ts:10-12`, applied at `manage-allocation.ts:588-590`) doesn't move, but by late morning margin is buying ≤7-DTE OTM contracts with a hard 12:55 exit — a 0.35-delta lottery ticket bought at 11:30 is mostly theta bleed unless the move comes immediately. Ramp the target delta up through the session (e.g. 0.35 morning → 0.50–0.55 after 11:00) so afternoon adds carry more intrinsic into the forced close. Env-tunable, and the candidate logs already record delta per pick, so the effect is measurable in the ledger (#9).
